# EvoTorch in downstream repositories

I searched public GitHub code for `from evotorch`, `import evotorch`, and `evotorch.algorithms` on 19 September 2026. I read pinned source files and each project's own README or entry point. GitHub marks all eight listed repositories as non-forks. This is a selected sample, not an adoption count. I did not run these repositories. An import and a configured search show integration; they do not prove a reported result or deployment.

Three more source hits illustrate why a search-result count is misleading. [ASAL++](https://github.com/fredericowieser/ASALPlusPlus/blob/16a0f918251bfa0f8deaf7e25c23ab40586a5a86/src/asal_pytorch/main_opt.py#L123-L200) contains an experimental PyTorch/EvoTorch CMAES route, but its [README](https://github.com/fredericowieser/ASALPlusPlus/blob/16a0f918251bfa0f8deaf7e25c23ab40586a5a86/README.md) says paper experiments use JAX and calls the PyTorch route experimental. [NaturalNets](https://github.com/neuroevolution-ai/NaturalNets/blob/efc2037b5c8a701c8c39f4f11e9685a1a729f72e/naturalnets/optimizers/cma_es_evotorch.py#L70-L120) implements an EvoTorch ask/tell shim, but its [README examples](https://github.com/neuroevolution-ai/NaturalNets/blob/efc2037b5c8a701c8c39f4f11e9685a1a729f72e/README.md) select DEAP. [HDTwinGen](https://github.com/samholt/HDTwinGen/blob/a7cd335fc9ba701b6e4a986a0485b28460290184/libs/cancer/env.py#L565-L670) contains a CPU PGPE branch for a cancer simulator. That source does not establish a completed run or clinical use. I excluded EvoTorch's own examples, vendored `src/evotorch` copies, and import-only matches.

The source evidence suggests a product direction, not an empty market. EvoTorch already supplies GPU-capable search algorithms, vectorized objectives, distributed actors, and neuroevolution. Downstream authors still write task-specific evaluators, custom operators, tensor-to-domain conversion, constraint handling, experiment scripts, and result checks. Some objectives are naturally differentiable; EvoIK does not show that DFO is necessary. Others are expensive or non-differentiable, as in Contimask, DDEA, and nested MLP tuning. I recommend testing `torch-dfo` as a **PyTorch-native evaluation and experiment layer for costly, batched, constrained, mixed-variable objectives**, with algorithm adapters where needed. It should prove value against EvoTorch on full evaluation cost, quality, reproducibility, and failure handling. A second algorithm catalog or an unsupported blanket GPU speed claim would duplicate demonstrated EvoTorch functionality.

The evidence does not establish deployment count, market size, performance superiority, or clinical validity. Search indexing is incomplete and favors public Python code. The eight rows establish distinct code-level integrations; only the projects' own materials report experiments. No downstream repository was executed in this review.
