# Two adapter evaluation proposal

20 September 2026. This is a protocol proposal, not a frozen benchmark or a result. No package was installed and no dataset was downloaded for this review.

## Decision

Build one control adapter for `myosuite:myoChallengeBaodingP2-v1` and one discrete-design adapter for `TFBind8-Exact-v0`. The first tests a costly, noisy CPU simulator. The second tests representation, data boundaries, and exact lookup. Neither currently justifies a GPU application claim. Keep the existing batched LJ38 objective as a *separate performance control*; its analytic-gradient basin-hopping baseline remains relevant, so GPU throughput there is not a DFO quality result.

Do not start biological optimization until the data and oracle checks below pass. If they fail, stop that adapter and report the failure. GFP and TFBind10 do not repair the evidence gap by themselves: GFP uses a learned oracle; TFBind10 uses another full lookup and has open data-integrity questions.

## Adapter boundary

Use the proposed local search session, but keep the evaluator out of algorithm state. The adapter accepts candidate IDs and decoded inputs, then returns objective values, validity, constraint results, and actual cost. It owns its own RNG. It rejects stale IDs and shape/dtype errors before updating an optimizer. Record attempted evaluations even if the simulator fails. Preserve the pending batch across checkpoint and restart without making a second call.

For Baoding P2, the adapter loads one environment per worker, seeds it for each rollout, resets policy recurrent state, and records episode return, task `score`, effort, drop, steps, and wall time. The initial reference can use serial MuJoCo workers; process concurrency is an execution choice, not evidence of GPU simulation. Use the published policy architecture as the common vector map, but train from scratch with the default reward. A compact policy is a possible later *separate* track only if frozen for all algorithms before quality measurements. Do not silently clip invalid action values; declare action encoding and report invalid outputs.

For TFBind8, the adapter accepts eight integers in `[0,3]`, checks uniqueness, and calls the native exact oracle. Expose only the registered lower-half training view to a search method. Seal the full oracle table and candidate lookup behind the evaluator. Preserve both the raw sequence and any continuous encoding; count duplicate decoded sequences. Missing-key fallback and nonfinite labels are errors until the dataset audit establishes what they mean. A 32-logit argmax encoding can compare continuous torch-dfo and EvoTorch optimizers; a direct base-substitution baseline must also run, because categorical search is the natural specialist.

## Frozen comparison before each search

1. Freeze source hashes, assets/data hashes, objective direction, policy or sequence map, default environment settings, candidate validation, method configs, budget, seed lists, and a decision script. Keep development and confirmation output directories separate. No held-out call informs tuning.
2. Baoding: use three named development optimizer seeds and fixed rollout seeds during tuning. Use common random numbers across methods. After at most three development changes, seal one config per method. Run ten fresh optimizer seeds per method, then evaluate each saved incumbent on ten new environment seeds. Compare mean task score, lower-decile score, drop rate, effort, and reward. Publish per-episode outcomes, not only a mean. Environmental randomization comes from P2 registration; a fatigue variant is a separate task and is not part of this native-task claim. A score improvement with more drops or worse tail behavior fails the robust-control claim.
3. TFBind8: use the native visible lower-half data only. Freeze ten optimizer seeds and a separate validation-query allowance. Compare best valid oracle score and top-k unique-sequence scores against best visible training sequence, uniform random, direct one-base mutation/hill climbing, and EvoTorch on the same 32-logit representation. Include torch-dfo's encoded optimizer under the same map. Report top-k Hamming diversity, duplicate fraction, and oracle calls. Do not impose GC or mutation constraints and still call it the official task; such constraints define a new variant.
4. Match **attempted true objective calls**, including failed and repeated rollouts or oracle lookups. Save best-so-far traces by calls and elapsed time. Match the policy/decoder, initialization distribution, reward, task version, rollout seeds, and population budget. Run EvoTorch PGPE for control; use an EvoTorch continuous searcher compatible with the TFBind8 logits. Compare native direct-sequence variation separately. A published RL baseline such as NPG/PPO matters for task quality, but account for its simulator steps and total training cost; do not pretend RL updates equal black-box policy calls. If a useful gradient exists for a changed objective, include a gradient baseline in that changed track.
5. Pin a decision rule before confirmation: a torch-dfo variant earns a Baoding application claim only if the paired 95% confidence interval for mean task-score gain has a lower bound above zero and its observed gain is at least 0.05 on the task's 0–1 score. Its drop rate cannot rise by more than two percentage points, and its lower-decile score cannot fall. Cluster resampling by optimizer seed avoids treating 100 rollouts as 100 independent trained policies. A lower-cost claim instead requires noninferior quality under predeclared margins and at least 20% less full-run wall time; this is a proposed threshold to freeze before runs. Report effect sizes and all uncertainty. The first adapter pass is primarily a contract test; it need not win.

The baseline count and exact optimization budgets must be frozen *after a score-blind runtime smoke*, using measured rollout throughput and an agreed wall-time ceiling. The smoke may run a fixed policy on 64 seeded P2 episodes and 256 TFBind8 oracle lookups; do not choose a budget from score quality. For a bounded initial comparison, cap each method/seed at 256 P2 candidate policies with two seeded episodes each, and 512 TFBind8 oracle calls. These are pilot budgets, not credible proof of solving a difficult P2 task. If the runtime smoke shows P2 cannot complete this cap within the agreed ceiling, report a feasibility no-go rather than reducing only one method's work. Larger training budgets require a separately frozen protocol.

## Cost and Spark gate

Measure cold process start, import, data/model load, simulator setup, and the first objective batch separately. Then measure warm objective, optimizer update, transfers, and full experiment with the same candidates. Synchronize CUDA before and after timed GPU regions. Record p50 and p95 batch latency, candidates or simulator steps per second, memory peak, utilization, and end-to-end wall time. Use equal concurrency. Record dataset acquisition time separately and disclose it.

NVIDIA documents DGX Spark as arm64 and ships a [CUDA 13 container runtime](https://docs.nvidia.com/dgx/dgx-spark/nvidia-container-runtime-for-docker.html); its [release notes](https://docs.nvidia.com/dgx/dgx-spark/release-notes.html) describe CUDA 13.0.2 and PyTorch in JupyterLab. Earlier work in this session ran torch 2.13 with CUDA 13 on the owner's Spark. That confirms a PyTorch path, not the MyoSuite/JAX/TensorFlow/DeepChem dependency set. Test those in isolated environments only after wheel and asset availability checks. Do not change host services for this protocol.

Current MyoSuite has an [`MJX`/`MJWarp` implementation](https://github.com/MyoHub/myosuite/blob/94300995076b20ed6a8cfc65794c54bc997a0697/myosuite/envs/myo/mjx/README.md) and registers [`MjxHandReachRandom-v0`](https://github.com/MyoHub/myosuite/blob/94300995076b20ed6a8cfc65794c54bc997a0697/myosuite/envs/myo/mjx/__init__.py#L152-L165). Its published GPU timing is for elbow, finger, and hand reach, **not Baoding P2**. A later hand-reach GPU adapter must first show matching task semantics and identical evaluator values across the torch-dfo and EvoTorch paths. Crossing PyTorch and JAX may add transfer and compilation cost; measure it. TFBind8's Python dictionary lookup is not a GPU-compute need. LJ38 remains the existing tensor-batched GPU throughput control, with its classical solver comparison clearly separate.

## Hard stops, maximum three development iterations per adapter

**Phase 0, before search:** stop if MyoSuite P2 cannot instantiate and replay fixed seeded rollouts; stop TFBind8 if permitted complete data cannot be acquired and hashed, unique-key/duplicate behavior and score direction cannot be checked, or native oracle scores disagree with table samples. Stop if a method can read held-out oracle labels or if budget/failure accounting fails an adversarial probe.

**Development:** allow at most three predeclared config or adapter iterations per task. Each iteration costs a full stated development budget and remains in the record. Do not move the confirmation seeds, rewrite scores, or exclude failed runs after seeing results. If a nonfinite reward, evaluator mismatch, or lost call count appears, fix the evaluator and restart under a new version; preserve the failed version.

**Acceptance:** if torch-dfo does not improve verified quality at equal true cost, or match it at materially lower end-to-end cost, do not claim a product win. If both adapters demand incompatible session semantics, revisit the abstraction before adding features. If neither exposes substantial batched compute, defer a GPU-product claim. Solving P2 or ranking TFBind8 sequences would be a benchmark result; it would not establish a novel algorithm, a new biological function, or clinical utility.
