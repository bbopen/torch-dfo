# Independent architecture review

Verdict: **conditional acceptance of the direction, not the contract yet**. A synchronous run with one pending batch, CMA-ES, and random search is a credible first implementation. It addresses the ownership failure in the current library without claiming a new optimizer result. The conditions below are testable and must be settled before the contract suite can accept it.

## Corrections required before implementation acceptance

1. **Separate an attested logical count from an actual-call guarantee.** The budget unit is one candidate and replicate evaluation, even when one Python invocation processes a batch (`architecture-decision.md:31-41`). An external `tell()` can misreport an attempted-call mask. An objective can also run multiple internal simulator steps. State that the hard cap applies to the supplied, trusted executor's scheduled logical evaluations. Treat external results as attested counts. If the executor loses authoritative facts, charge the full reservation and stop. Keep simulator steps and post-hoc validation costs separate, as `program.md:27-33` requires. Resolve the earlier `contracts-proposal.md` pseudocode, which refunds a full reservation based only on returned flags.

2. **Close the pending-checkpoint replay gap.** The decision permits saving an unstarted pending proposal and forbids silent replay after an uncertain completion (`architecture-decision.md:45-51`). A checkpoint saved before execution looks identical after a crash during the objective unless a durable start transition exists. For the first implementation, either save only quiescent completed states, or persist an execution-start marker before invoking the objective. Restoring a started, unresolved batch must charge conservatively and stop until an explicit external result arrives. Returning the same IDs alone does not prove that replay is safe. The older proposal forbids pending checkpoints (`contracts-proposal.md`, “RNG and checkpoint contract”); make the accepted rule unambiguous.

3. **Define the transaction after `ask()` and `tell()` errors.** `CandidateBatch.x` is an owned tensor, but the caller can still mutate it. Keep a private authoritative candidate copy, or check its exact contents before `tell()`. Reorder values by ID and pass the original candidate order to the adapter. Reject IDs, shapes, repeat counts, and constraints before any adapter update. Once an executor error makes work uncertain, a later `tell()` must not reclaim or re-run that reservation without an explicit result. If adapter `tell()` throws, charge attempted work and mark the algorithm state terminal or restore a pre-update snapshot. Do not serialize it as a resumable success. This is necessary because current `CMAES.tell()` mutates fitness, mean, and path state before its late operations (`src/torch_dfo/cmaes.py:489-585`). An injected error in `_record_path_vector` after one `ask()` changed `mean` and `fitness`, while `_generation` stayed at zero. `abort()` only clearing pending state, as the older proposal says, cannot repair that state.

4. **Name the noisy incumbent and the seed schedule.** The decision promises the “best valid feasible observation” (`architecture-decision.md:29`), while `contracts-proposal.md` ranks a candidate by the mean over all repeats. Those are different estimands. Define the incumbent as a candidate chosen by the declared repeat aggregate, and retain each raw observation separately. A single lucky replicate must not become the reported robust best. The older proposal derives every seed from candidate ID, but `architecture-decision.md:53` also requires common scenario seeds for controller comparisons. Specify two distinct policies: independent seeds keyed to a candidate and repeat, or a shared scenario schedule keyed to scenario and split. Hold-out rescoring needs its own cost and record.

5. **Scope the first adapter and overhead claims tightly.** CMA-ES needs a full generation; random search can spend the residual budget (`architecture-decision.md:11-19,31-37`). Initial scalar adapters must reject every nonempty constraint tensor, including all-feasible constraints (`architecture-decision.md:55-59`). A result schema alone is not constrained optimization. CPU IDs, value and status checks, tensor copies, and checkpoint serialization can synchronize a CUDA batch. Measure the full run on cheap batched tensor objectives and on an expensive CPU objective. Predeclare an acceptable overhead before claiming a low-cost tensor path. The two application adapters and exact evaluation protocol remain a separate phase gate under `program.md:13-23`.

## Falsifiable contract tests

- With budgets one below, equal to, and one above `population_size * repeats`, CMA-ES must draw nothing when it cannot fit. Random search must spend the allowed residual. An instrumented evaluator must agree with scheduled, known attempted, charged, completed, and reserved counts on normal and throwing paths.
- Save a proposed batch, mark execution started, then inject a crash after one actual objective attempt. Restore from the durable state. It must never call that entry again, and it must show the conservative charge. A never-started saved proposal must restore identical IDs and values without drawing again.
- Mutate returned candidate values, reorder valid result IDs, then submit duplicate, stale, missing, and shape-invalid results. No invalid result may reach an adapter. A valid reorder must give the same next candidate values as the ordered result.
- Inject an adapter update error after its first state mutation. Confirm charged cost remains and the run cannot resume or checkpoint a partially updated adapter as healthy.
- Evaluate stochastic candidates using common scenarios with two microbatch sizes and different result orders. Each candidate must see the same scenario IDs and seeds. Independent-seed mode must give distinct per-candidate seeds. Both modes must leave global RNG state unchanged.
- For a failed replicate, NaN, infinite constraint, and all-infeasible constrained batch, retain the raw facts. Initial CMA-ES must stop before update. With all failures, report no incumbent. With one lucky replicate and a worse repeat, the robust incumbent must follow the declared aggregate.
- Compare the new run with direct legacy CMA-ES and EvoTorch at equal logical evaluation work. Record objective time, run time, clones, transfers, validation, syncs, and checkpoint cost. A quality or speed advantage requires repeated measurements and the program's separate application gate.

This review examines the proposed contract and a local fault injection, not an implementation of `SearchRun`. It makes no scientific performance claim.

## Disposition after the revised decision

The revision resolves the main budget-trust boundary (`architecture-decision.md:33-43`), pending-checkpoint replay risk for version one (`:47-55`), poisoned adapter state (`:41`), repeat aggregate and seed policy (`:29,57`), and first-adapter constraint scope (`:61`). I accept the revised **direction** for implementation. I have not reviewed an implementation or accepted its contract suite.

One candidate-integrity detail remains open. The run keeps a private original tensor and gives the caller a separate mutable tensor (`:23`). A caller can evaluate a modified public tensor, then return valid IDs and values. The adapter would update from the private original. Require the run to detect any change to the public proposal before it accepts `tell()`, or make its managed evaluator execute from the private copy. Test a mutation before evaluation and a mutation during evaluation. IDs alone do not bind values to the candidate that produced them.

Two wording changes would prevent later confusion. In version one, checkpoint `pending state` (`:55`) must always be `none`; the contract should say so. The acceptance check that says “real objective attempts” (`:79`) should say “scheduled logical evaluations, known attempts, and conservative charges.” The library cannot inspect hidden work inside an arbitrary callback (`:35`). The original pending-checkpoint crash test above applies only to a later version with a durable execution journal. For version one, replace it with rejection of pending checkpoints and explicit fork lineage on loading an older snapshot.
